# ЛР5. Независимые правила и результаты

Вариант: **Fraud**.

## Что дано

Сервис создаёт фиксированный набор правил. Список `triggered_rules` ошибочно сохраняется между вызовами. Основной метод `FraudService.check()` также нужно реализовать; готовые проверки объектов и зависимостей не переписывайте.

## Задание

### Шаг 1. Сохраните зависимости и настройте сборку

В `FraudService(rules)` фиксируйте контейнер правил как `tuple`. Перенесите создание стандартных правил в `build_service()`; переданные объекты сохраняйте.

Промежуточные `score` и `codes` создавайте внутри каждого вызова. Пустой набор правил должен давать `0 / ALLOW` для корректного контекста.

### Шаг 2. Реализуйте `FraudService.check()`

Проверьте тип контекста (`INVALID_CONTEXT`), получите вклад каждого правила через `evaluate()` и готовую `risk_points()`. Ограничьте итог ста баллами; коды ненулевых вкладов сохраняйте без повторов в порядке правил. Даже после достижения 100 остальные правила должны быть вызваны.

### Шаг 3. Проверьте отказ и следующий вызов

Контрольный исполнитель сначала выбрасывает `DomainError("TEMPORARY")`, затем успешно работает. Первый вызов не повторяется автоматически и не меняет данные; второй использует того же исполнителя. `TEMPORARY` — код учебной проверки, не новая ветка бизнес-логики. Отсутствие зависимости проверяйте через `is None`, а не её истинность.

### Шаг 4. Обязательная практическая часть

В `FraudService` реализуйте `check_many(contexts)` — кортеж отдельных результатов `check()`. `highest_risk(contexts)` возвращает `(index, FraudResult)` с максимальным `score` (при равенстве первый), для пустого набора — `None`. Результаты разных контекстов не смешиваются.

## Примеры и границы

- Контрольное правило с вкладом `60` даёт `DECLINE` и свой код.
- Изменение исходного списка правил не влияет на сервис; результаты разных экземпляров не смешиваются.
- Отрицательный или нецелый вклад вызывает `INVALID_RULE_RESULT`.
- `DomainError` из правила передаётся вызывающему коду, а не заменяется на `ALLOW`.

Последовательности и конфигурации дополнительно проверяются в `tests/test_progression.py`. Прочитайте ожидаемый результат каждого сценария до реализации.

Все проверки открыты: `tests/test_contract.py` и `tests/test_review_contract.py`.
